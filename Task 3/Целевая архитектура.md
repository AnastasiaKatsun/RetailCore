## **1. Краткое резюме трансформации**

В рамках проекта RetailCore система должна поддержать управляемое масштабирование типовых коммерческих сценариев (промо, партнёрские интеграции) и снизить операционные риски core checkout. В текущем состоянии этому мешают высокая связность монолита с Oracle, отсутствие единого источника правды для статусов и аналитики, а также синхронные зависимости от внешних систем. Для первого этапа выбраны точки трансформации: слой событий заказа (Event Hub), вынос промо‑логики в отдельный сервис и унификация контрактов маршрутизации доставки. Целевая архитектура не заменяет монолит и Oracle сразу, а изолирует критичные зависимости, вводит событийную модель и контракты с fallback, что позволяет проверить результат по метрикам p95/p99, расхождений витрин и времени вывода промо.

## **2. Бизнес‑цель и критерии успеха**

| Элемент | Описание |
| --- | --- |
| Бизнес‑цель | Снизить операционные риски и ускорить вывод типовых изменений без деградации core checkout. |
| Пользовательская ценность | Стабильные статусы заказа, предсказуемые сроки доставки, корректные скидки с первого шага. |
| Операционный эффект | Снижение инцидентов в поддержке, уменьшение расхождений витрин, ускорение запуска промо. |
| Горизонт проверки | 4–6 недель после канареечного релиза; стабилизация метрик. |
| Ограничения результата | Не меняем core платёжную оркестрацию и не делаем полную миграцию с Oracle. |

## **4. Ограничения и допущения**

| Тип | Формулировка | Влияние на архитектуру |
| --- | --- | --- |
| Техническое ограничение | Нельзя менять core платёжную логику в первом этапе | Выносим только промо, доставку и события; платёж остаётся в монолите |
| Организационное ограничение | Канареечный релиз 20% трафика; план отката обязателен | Внедряем feature flags, теневые сравнения и мониторинг p95 |
| Инфраструктурное ограничение | Oracle остаётся как операционная БД; PostgreSQL — для аналитики | Используем CDC и staging‑слой вместо полной миграции |
| Доменное ограничение | Статусы для клиента и операций должны быть непротиворечивы | Вводим каноническую модель статусов и контракты между сервисами |
| Допущение | Промо‑сервис может возвращать результат с задержкой ≤200мс | Закладываем fallback и таймауты; проверяем на канареечном трафике |

### **6.1 Точка трансформации: Слой событий заказа**

| Вопрос | Ответ |
| --- | --- |
| Какой бизнес‑цели помогает? | Снижение расхождений витрин и нагрузки на Oracle |
| Где находится в AS‑IS? | Витрины делают прямые SQL‑запросы; статусы в разных таблицах |
| Что именно плохо работает сейчас? | Расхождения цифр, тяжёлые запросы, сложно воспроизвести историю |
| Что изменится в TO‑BE? | События публикуются из монолита; витрины строятся на потоке событий |
| Что не меняется на этом этапе? | Oracle остаётся операционной БД; миграции данных нет |

| Что будет считаться неуспехом? | Расхождения \>3% или рост p95 checkout \>2.2с |

### **6.2 Точка трансформации: Промо‑сервис (расчёт скидок)**

| Вопрос | Ответ |
| --- | --- |
| Какой бизнес‑цели помогает? | Ускорить вывод промо‑кампаний и снизить ошибки в расчётах скидок; уменьшить зависимость core checkout от тяжёлой логики и Oracle‑процедур |
| Где находится в AS‑IS? | Логика скидок частично в Java Monolith, частично в Oracle‑хранимых процедурах; правки требуют релиза монолита и ночных выкладок |
| Что именно плохо работает сейчас? | Фрагментированная логика → долгие релизы, расхождения в скидках между каналами, ручные ночные правки, высокая нагрузка на Oracle |
| Что изменится в TO‑BE? | Выделяем отдельный Promo Service для расчёта скидок; вводим теневой режим для сравнения с текущим расчётом; fallback на монолит при недоступности сервиса; контракты gRPC/REST с явными таймаутами |
| Что не меняется на этом этапе? | Core платёжная логика и оркестрация остаются в монолите; Oracle остаётся источником справочников; не меняем финансовую отчётность и правила аудита скидок |
| Какие ограничения учитываются? | Канареечный релиз 20% трафика; таймаут ≤200мс; fallback обязателен; нельзя увеличивать p95 checkout более чем на 10% |
| Как проверяем результат? | Время вывода типового промо ≤3 рабочих дней; доля расхождений между новым и старым расчётом ≤5%; p95 времени ответа ≤2.0с |
| Что будет считаться неуспехом? | Расхождения \>5% на канареечном трафике; рост p95 core checkout \>2.2с; падение SLA Promo Service \>1%; невозможность откатить без деградации checkout |

### **6.2 Точка трансформации: Сервис доставки и маршрутизации**

| Вопрос | Ответ |
| --- | --- |
| Какой бизнес‑цели помогает? | Снизить дубли заявок и ручные правки статусов, сделать сроки доставки предсказуемыми для клиента, уменьшить эскалации поддержки |
| Где находится в AS‑IS? | Маршрутизация и статусы частично в монолите, частично в Oracle; прямые синхронные вызовы к партнёрам; разные семантики статусов у разных логистических провайдеров |
| Что именно плохо работает сейчас? | Разные статусы у партнёров → дубли заявок, рассинхронизация сроков, ручные исправления ночью; синхронные вызовы в потоке checkout увеличивают p95; нет дедупликации и единого контракта |
| Что изменится в TO‑BE? | Вводим Delivery & Routing Service с единым контрактом статусов; асинхронные подтверждения от партнёров через очереди; дедупликация по ключу идемпотентности; отдельные политики повторов и таймаутов; статусы нормализуются к канонической модели |
| Что не меняется на этом этапе? | Платёжная оркестрация и core‑логика создания заказа остаются в монолите; Oracle остаётся источником правил маршрутизации; не меняем финансовые отчёты по доставке |
| Какие ограничения учитываются? | Сначала выносим только новые интеграции; старые партнёры остаются на синхронных вызовах с постепенным переходом; дедлайн по p95 ≤2.0с; обязателен план отката |
| Как проверяем результат? | Доля дублей заявок ≤0.1%; доля эскалаций по статусам доставки ≤15/нед; доля заказов с подтверждённым маршрутом в течение 5мин ≥95% |
| Что будет считаться неуспехом? | Доля дублей \>0.2%; рост эскалаций \>25/нед; падение SLA Delivery Service \>2%; невозможность восстановить согласованность статусов в течение 15мин после сбоя партнёра |

## **10\. Целевая архитектура первого этапа**

### **10.1. Границы TO‑BE**

**Входит в целевое состояние:**

* Слой событий заказа (Event Hub) на Kafka/RabbitMQ
* Промо‑сервис с fallback и теневым сравнением
* Сервис доставки с единым контрактом статусов и дедупликацией
* Канареечные релизы, feature flags, мониторинг p95

**Не входит в целевое состояние:**

* Полная миграция с Oracle
* Замена всех интеграций на единый брокер
* Перепроектирование финансовой отчётности
* Изменение core платёжной оркестрации

### **10.2. Компоненты TO‑BE**

| Компонент | Новый / существующий | Ответственность | Основные данные | Ключевые связи |
| --- | --- | --- | --- | --- |
| Java Monolith | Существующий | Core checkout, платёж, публикация событий | Транзакции заказа, статусы | Promo Service, Delivery Service, Event Hub, Oracle |
| Promo Service | Новый | Расчёт скидок, управление промо | Справочники, коэффициенты | Oracle, Monolith (fallback) |
| Delivery Service | Новый | Маршрутизация, статусы доставки | Правила, справочники | Oracle, логистические партнёры, Event Hub |
| Event Hub | Новый | Единый источник событий заказа | События жизненного цикла | Analytics, Monolith, Delivery, платёжные провайдеры |
| Batch & Scheduled Jobs | Существующий | Актуализация справочников, повторные попытки | Oracle, очереди | Oracle, Event Hub |

### **10.3. Ключевые архитектурные решения**

| № | Решение | Почему выбрано | Какие ограничения учитывает | Какие риски создаёт |
| --- | --- | --- | --- | --- |
| 1 | События как единый источник правды | Снижает расхождения витрин и нагрузку на Oracle | Oracle остаётся; нужна идемпотентность | Рассинхронизация при потере событий — нужен контроль доставки |
| 2 | Fallback для промо‑сервиса | Позволяет не блокировать checkout при проблемах с сервисом | Core checkout нельзя трогать | Расхождения в расчётах — нужен теневой режим и метрики |
| 3 | Дедупликация в сервисе доставки | Исключает дубли заявок у партнёров | Разные семантики статусов у партнёров | Нужно хранить ключи идемпотентности |

## **14. Проверка качества документа**

Перед сдачей проверьте, что:

* бизнес‑цель сформулирована ясно и связана с архитектурными изменениями (снижение рисков core checkout, ускорение промо, предсказуемость доставки);
* AS‑IS описан только в объёме, нужном для выбора точек трансформации (фрагментированная логика, синхронные вызовы, тяжёлые SQL, разные статусы);
* каждая точка трансформации отличается от обычной доработки и технического долга (Event Hub, Promo Service, Delivery Service — это архитектурные изменения с измеримым эффектом);
* для каждой точки трансформации есть метрика проверки (p95, расхождения, дубли, эскалации);
* ограничения не спрятаны в тексте, а явно влияют на решения (Oracle остаётся, платёж не трогаем, канареечный релиз обязателен);
* TO‑BE описывает достижимое состояние первого этапа (новые сервисы + слой событий, без полной миграции);
* диаграмма TO‑BE показывает границы, компоненты, легаси‑зависимости и ключевые потоки (монолит, Oracle, новые сервисы, Event Hub, PostgreSQL);
* roadmap и cutover‑plan могут быть построены на основе этого документа (есть этапы, метрики, риски, владельцы).
